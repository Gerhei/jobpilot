# Правила написания качественных тестов

Для паттернов pytest и примеров кода читай `pytest-patterns.md`.
Для антипаттернов с примерами bad/good читай `anti-patterns.md`.

---

## Философия

**Тест проверяет контракт, а не реализацию.**
Контракт — публичное обещание: «при входе X всегда получается выход Y». Тест, знающий о внутренних переменных или приватных методах, сломается при любом рефакторинге, даже если поведение не изменилось.

**Тест — это спецификация решения.**
Каждый тест фиксирует решение, которое могло быть принято иначе. Если завтра кто-то изменит логику, тест должен упасть именно потому, что нарушено задокументированное решение.

**Тест должен падать по одной причине.**
Если тест может упасть из-за нескольких несвязанных вещей — это несколько тестов, склеенных в один.

**Хрупкий тест хуже отсутствующего.**
Тест, падающий при невинном рефакторинге, создаёт ложный шум и приучает игнорировать падения.

**Не каждый код нуждается в тестах.**
Не стоит тестировать: одноразовые скрипты, тонкие обёртки без логики (делегирует вызов и ничего не трансформирует), сгенерированный код. Критерий: если стоимость поддержки теста выше стоимости ручного обнаружения бага — тест не окупается.

## Структура теста

**AAA: Arrange → Act → Assert.**
Три явные части: подготовка данных и зависимостей, вызов тестируемого кода, проверка результата. Части не перемешиваются. Если между Act и Assert снова происходит Act — это два теста.

**Имя теста описывает сценарий, а не функцию.**
Формула: `test_<что>_<условие>_<ожидаемый результат>`

```python
# Плохо
def test_normalize_part_number(): ...

# Хорошо
def test_part_number_with_dashes_returns_clean_uppercase(): ...
```

Для сложных сценариев — короткое имя + docstring (pytest показывает docstring при падении).
Для параметризованных тестов — имя описывает правило в целом, конкретику несут `ids` в `parametrize`.

**Тест не должен требовать контекста для понимания.**
Данные, влияющие на исход, должны быть явно видны в теле теста. Инфраструктуру (соединения, клиенты) и дефолтные значения, не влияющие на сценарий — можно выносить в фикстуры.

**Используй фабрики для тестовых данных.**
Когда объект имеет десяток полей, а тест проверяет одно — фабрика задаёт разумные дефолты и позволяет указать только важное. Смотри примеры в `pytest-patterns.md`.

## Что тестировать

**Тестировать стоит всё, что имеет нетривиальное решение.**
Критерий: «могло ли это быть реализовано иначе?» Если да — тест нужен. Как только появляется ветвление, трансформация данных, обработка edge-cases — тест обязателен.

**Edge cases важнее happy path.**
Ошибки прячутся на границах: пустая строка, None, пустой список, максимальное значение, дубликаты, неожиданный формат. Минимальный набор: пустой ввод, типичный ввод, невалидный ввод, граничные значения.

**Поведение при ошибках — часть контракта.**
Если функция должна бросать исключение — это нужно покрыть. Если возвращать default при отсутствии данных — тоже.

## Стабы, моки и зависимости
Проверяй взаимодействие только когда сам вызов и есть контракт: событие отправлено в очередь, метрика записана, уведомление послано. Если тебя интересует результат — проверяй результат, а не вызовы.

**Заменяй зависимости, которые ты не контролируешь или которые делают тест медленным/нестабильным.**
Заменять: внешние API, БД, файловую систему, время, случайность, LLM-вызовы.
Не заменять: бизнес-логику внутри системы, простые data-классы, утилиты без побочных эффектов.

**Много моков = сигнал об архитектурных проблемах.**
Если для теста нужно 5+ моков — функция делает слишком много или зависимости не инвертированы.

**Для сложных stateful-зависимостей фейки предпочтительнее моков.**
`InMemoryRepository` вместо PostgreSQL-репозитория: реально работает, просто в памяти. Устойчивее к рефакторингу, менее хрупкий.

## Изоляция и детерминированность

**Тесты не зависят друг от друга.**
Каждый тест запускается в чистом состоянии. Запуск в любом порядке, подмножеством или параллельно даёт одинаковый результат. Shared mutable state — главная причина «мерцающих» тестов.

**Тест детерминирован.**
Зависимости от текущего времени, случайных чисел, порядка элементов в `set`, сетевых вызовов, файловой системы — источники недетерминизма. Каждый должен быть явно контролируем (заморожен, засеян, замокан).

**Scope фикстур соответствует их природе.**
`session`/`module` scope допустим только для immutable и stateless ресурсов: соединения к БД, HTTP-клиенты, конфигурации. Всё мутабельное — `function` scope.

Для async-специфики и pytest-asyncio смотри `pytest-patterns.md`.

## Скорость и диагностика

**Медленные тесты — тесты, которые перестают запускать.**
Юнит-тесты должны работать за секунды. Медленный юнит-тест — сигнал, что он перерос в интеграционный или зависимости не изолированы.

**Упавший тест быстро объясняет причину.**
Хорошее имя — первый уровень диагностики. При сравнении сложных структур используй assertion с описанием:

```python
# Голый assert — плохой diff при сложных объектах
assert result == expected

# С описанием — сразу видно что именно не так
assert field in result, f"поле {field} отсутствует после нормализации, ключи: {list(result.keys())}"
```

**Проверяй только поля, относящиеся к проверяемому поведению.**
`assert result == expected` на объекте с 50 полями — хрупкий тест. Проверяй конкретные поля, являющиеся частью контракта.

## Границы тестовой пирамиды

**Юнит-тест** проверяет одну единицу поведения в изоляции от внешних зависимостей. Юнит — не обязательно один класс. Это единица поведения: принимает вход, производит результат, все внешние зависимости заменены.

**Интеграционный тест** намеренно проверяет взаимодействие с реальной внешней системой: реальная БД, реальный HTTP, реальная файловая система.

Оба уровня нужны, но разделены: разные директории, разные маркеры (`pytest.mark.integration`), разные стадии CI. Юниты — на каждый коммит, интеграционные — реже.

## Организация тестов

**Структура тестов отражает структуру кода.**
```
tests/
├── unit/
│   └── parsing/
│       └── test_normalizer.py   # → src/parsing/normalizer.py
└── integration/
    └── parsing/
        └── test_normalizer.py
```

**`conftest.py` — иерархия, а не свалка.**
- `tests/conftest.py` — фикстуры общие для всех (конфигурация, фабрики базовых объектов)
- `tests/unit/conftest.py` — фикстуры для юнит-тестов
- `tests/integration/conftest.py` — соединения к тестовой БД, HTTP-клиенты
- Фикстура, нужная одному модулю, живёт в `conftest.py` этого модуля или прямо в тестовом файле

Признак проблемы: `conftest.py` на 500+ строк, половина фикстур используется одним тестом.

**Маркеры и CI-стадии разделяют скорость обратной связи.**
Регистрируй маркеры в `pyproject.toml`, в CI — отдельные стадии: юниты на каждый коммит, интеграционные на PR или по расписанию.
