# Соглашения по коммитам

## Формат

```
КЛЮЧ-ЗАДАЧИ Краткое описание что сделано

Подробное описание — что и почему сделано.
```

## Заголовок

- Формат: `КЛЮЧ-XXX Описание` — до 80 символов
- Ключ задачи (например, `PROJ-42`) — если коммит привязан к задаче; иначе опускается
- Описание с заглавной буквы, точка в конце **не ставится**
- Глагол — краткое страдательное причастие прошедшего времени: исправлено, удалено,
  добавлено, вынесено, заменено. Может быть опущен, если это очевидно. Например, вместо 
"Добавлена базовая инфраструктура проекта" -> "Базовая инфраструктура проекта"
- Описывает результат/контекст задачи, не перечисление изменённых файлов
- Язык: **русский**

```
PROJ-42 Исправлена ошибка округления суммы в счёте при скидке
PROJ-87 Сортировка товаров по дате поступления
Обновлена зависимость urllib3 до 2.6.3
Рефакторинг слоя хранения результатов
```

## Тело коммита

Отделяется от заголовка пустой строкой. Ширина строки до 80 символов.

**Тело не нужно**, если заголовок самодостаточен. На практике это большинство
атомарных задач: добавление поля, удаление зависимости, мелкий рефакторинг.

```
PROJ-11 Удалены выводы в консоль для дебага
PROJ-22 Удаление адреса доставки из данных заказа
Обновлена версия зависимости urllib3 до 2.6.3
```

Писать обязательно если:
- принято неочевидное техническое решение — объяснить почему
- баг имеет нетривиальную причину — объяснить цепочку событий
- изменение затрагивает несколько модулей и связь между ними неочевидна
- были побочные правки — описать их

### Одно уточнение

Заголовок верный, но нужна одна деталь о причине или ограничении:

```
PROJ-14 Исправлена ошибка сохранения профиля с необязательным полем отчеств

Форма передавала пустую строку вместо null, что нарушало ограничение
уникальности на уровне БД при нескольких пользователях без отчества.
```

```
PROJ-27 Исправлено зависание воркера при недоступности брокера

Celery по умолчанию блокирует поток на попытке переподключения без таймаута,
поэтому воркер не завершался корректно при остановке контейнера.
```

### Нарратив

Баг с нетривиальной причиной — объясняем цепочку событий:

```
PROJ-88 Устранено дублирование записей при параллельном создании пользователей

Два запроса могли одновременно обнаружить отсутствие записи и оба выполнить
INSERT. Уникальный индекс отклонял второй запрос с IntegrityError, который
глушился в except-блоке без отката транзакции.

В исправлении INSERT заменён на INSERT ... ON CONFLICT DO NOTHING.
```

Когда причина — поведение внешней библиотеки или платформы, добавляем ссылку:

```
PROJ-55 Исправлена ошибка десериализации дат в ответе стороннего API

В Python 3.11 поведение datetime.fromisoformat изменилось: теперь метод
принимает суффикс 'Z' как валидный UTC-offset:
https://docs.python.org/3/library/datetime.html#datetime.datetime.fromisoformat

До этого изменения строки вида '2024-01-15T10:00:00Z' вызывали ValueError
при получении временных меток от внешнего сервиса.

В исправлении добавлена явная замена суффикса 'Z' на '+00:00' для
совместимости с Python 3.10.
```

Для особо сложных причин допустима нумерация шагов:

```
PROJ-99 Исправлен некорректный подсчёт остатка на складе при отмене заказа

При отмене заказа остаток возвращался через UPDATE stock SET quantity = quantity + N.
Если между созданием заказа и его отменой другой процесс успевал списать тот
же товар, UPDATE применялся к уже изменённому значению и остаток завышался:
1. Заказ создан: остаток 10 → списано 3 → остаток 7.
2. Параллельно списано ещё 2 → остаток 5.
3. Отмена первого заказа: 5 + 3 = 8, хотя должно быть 5 + 3 = 8 — верно
   только случайно, т.к. второе списание не учитывает первую отмену.

Проблема проявлялась при частичном возврате, где N бралось из кэша на момент
создания заказа, а не из текущего состояния. В исправлении значение N
перечитывается из БД внутри транзакции с SELECT FOR UPDATE.
```

### Список изменений

Когда в коммите несколько независимых, но связанных правок:

```
PROJ-34 Исправления обработки ошибок при отправке email-уведомлений

При сетевой ошибке задача завершалась без повторной попытки, так как
исключение не перехватывалось на уровне Celery-таска.

- добавлен autoretry_for с экспоненциальной задержкой на сетевые ошибки
- добавлено логирование номера попытки и причины ошибки
- исправлен некорректный статус задачи при исчерпании попыток
```

```
PROJ-44 Правки схемы валидации адреса доставки

- поле city сделано обязательным
- добавлена валидация формата почтового индекса по регулярному выражению
- удалено устаревшее поле region_code
- значение по умолчанию для floor изменено с 0 на None
```

### Несколько абзацев

Рефакторинг или большая задача — каждый логический блок отдельным абзацем:

```
PROJ-70 Вынесен слой работы с сессиями в отдельный модуль

Логика создания, продления и инвалидации сессий была рассыпана по нескольким
эндпоинтам с дублирующимися условиями и разными TTL. Изменение стратегии
требовало правок в каждом месте отдельно.

Теперь всё взаимодействие с сессиями сосредоточено в SessionRepository с
единым интерфейсом create/refresh/revoke. Эндпоинты зависят только от этого
интерфейса, TTL и стратегия инвалидации настраиваются в одном месте.

Также добавлено версионирование ключей через префикс — это позволяет
инвалидировать все активные сессии разом при смене алгоритма подписи без
ручной очистки Redis.
```

### Пометка о смежных работах

Если часть задачи сознательно откладывается — упоминаем прямо в теле:

```
PROJ-80 Переход на asyncpg вместо psycopg2

Существующие синхронные вызовы в фоновых задачах Celery временно обёрнуты
в run_in_executor. Полный перевод Celery-воркеров на asyncio запланирован
отдельно.
```

## Гранулярность

- Один коммит = одна логическая проблема
- Один баг = один коммит
- Попутно найденный баг в другом месте — отдельный коммит
- Несвязанный рефакторинг — отдельный коммит
- Тесты и фикстуры — в том же коммите, что и основное изменение

## Отдельным коммитом всегда

- Добавление или обновление зависимостей
- Изменения конфигов (Docker, env, CI)
- Рефакторинг без изменения поведения

## Побочные изменения

- Мелкие (1–5 строк, очевидный контекст) — описать в теле основного коммита
- Значимые (меняют поведение, затрагивают отдельный модуль) — выносить в
  отдельный коммит
